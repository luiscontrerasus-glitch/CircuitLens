# Actual Gemini circuit-photo evaluation

Assessed October 3, 2026. **These are real circuit photographs and real Google Gemini responses. They are not the generated seven-demo fixtures or mock perception.** Six appropriately licensed photographs are saved in `test-images/real-breadboards`; attribution, licenses, diagrams, intended values and hashes are in `test-images/README.md` and its manifest.

## Configuration and method

The ignored local key authenticated with Google's model API without exposing its value. The owner confirmed **Free Tier, billing disabled, no linked billing account**. This is a user attestation: neither the local flag nor a model request independently proves Google billing status. No billing setting was changed and no OpenAI request or paid fallback was used.

The first generation attempt revealed that `gemini-2.5-flash` is unavailable to new users (HTTP 404), despite its metadata returning 200. The adapter was updated to default `gemini-3.8-flash`, supported LOW thinking and temperature 1. Google's [pricing](https://ai.google.dev/gemini-api/docs/pricing) lists standard input/output as free for both [3.8 Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash) and [3.5 Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite), including image input. Only those two verified image-understanding models are allowlisted. Flash-Lite comparison was deliberately selected by the operator after repeated 503s; the application never changes models or providers automatically.

Inputs used the normal Sharp upload validation/resizing/metadata-removal path. Only photograph pixels and the extraction instructions were sent. No tutorial, component list, intended circuit, schematic or fault answer was supplied to Google. Responses passed the existing strict JSON schema and coordinate validation, then remained pending. Records preserve source/prepared image hashes, model, UTC timestamp, token counts, HTTP status and elapsed time. Prompt hashes are included in later requests; initial LED/button/RGB responses predate the unsupported-part instruction refinement.

Each image was tested. There were **18 deliberate CLI requests: 9 valid structured responses, 8 provider-overload HTTP 503s, and 1 obsolete-model HTTP 404**. Selected records contain one successful response for each of the six images; earlier attempts and the explicit Flash-Lite comparison remain archived. Selection is disclosed in the individual records. It is not a benchmark ranking or an automatic retry system. Browser request results are reported separately in `live-browser-verification.json`.

## Connections, diagnostics and interpretation

**0/6 complete verified circuit reconstructions. Diagnostic accuracy is not measurable for this set.** The tutorials document functioning intended circuits, not physically validated injected faults. Arduino output behavior, IC internals, pots, sensors and four-terminal LEDs lie outside the existing wire/resistor/two-lead-LED/effective-switch engine. Hidden contacts, LED polarity, wire occlusion and breadboard rails cannot be established solely from these photographs. No full wire-connection accuracy percentage or hardware safety claim is justified.

Every selected response is blocked while pending. Even blindly accepting all detections remains blocked by missing terminals, values, states or unsupported parts; this was checked against all six archived outputs. The unknown/pending safeguards worked. They do not detect every confidently wrong value or missing component: human review must check omissions and visible evidence too. Rejecting an unsupported IC or controller merely removes it from a partial model; it does not validate the original complete circuit.

The actual request/JSON/UI pipeline works, but these results **do not support autonomous circuit diagnosis from general breadboard photographs**. Do not advertise that capability. The dependable hackathon path remains the seven explicitly generated examples and human-confirmed manual netlists. A reversed LED diagnosed in those examples is deterministic model evidence, not a reversed LED recognized in these photos.

## Changes and remaining errors

- Replaced the obsolete default model; retained explicit free-only allowlist and zero OpenAI fallback.
- Used the current model's LOW thinking setting, temperature 1 and bounded 12,000-token response; no truncation or schema failures occurred in received responses.
- Distinguished unavailable-model and temporarily overloaded-service errors with sanitized explanations, manual entry, and no automatic retry.
- Strengthened instructions to retain unsupported devices and not flatten multi-pin components. Complex-photo unknown handling improved, but RGB misclassification and omissions persist.
- Added a concise workbench review scope notice and archived-photo regression checks so unresolved real outputs cannot silently create a diagnosis.

Recognition limitations remain visible rather than being filled with tutorial answers. This is a six-image convenience sample from one publisher, not a representative accuracy benchmark. No physical hardware, continuity, oscilloscope, SPICE or live OpenAI validation was performed. Account quotas and overloaded free models can prevent inference; do not enable billing to bypass them.
